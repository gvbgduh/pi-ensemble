1. The spirit of the approach
Read this section first for the mental model, then come back to it after finishing the rest of the guide. The mechanics in sections 2 to 6 are what make each sentence below true.

1.1 Built for a project, not a single task
This setup is for a project, not a task. The roster's unit of work is a project or multi-epic initiative, not a single bounded piece of work. The orchestrator holds the big picture at the project scale and drives the other models against it, so the setup coordinates multiple tasks and workstreams in parallel or in sequence rather than one bounded task at a time.

1.2 Partitioned contexts and multi-scale precision
Across its four sessions the roster holds roughly four times the working context of any single session, and because each role keeps a different scale of detail (project state, implementation, design and prose, evidence) the overlap between them stays small: detailed context is spread across the roster rather than duplicated, with the trackers and artifacts carrying the shared part. That is what lets one session span many tasks and keep shipping instead of resetting at every context limit. The arithmetic only holds while the roles stay at their own scale; the moment two sessions start doing the same work on the same material, the overlap grows and the extra capacity is spent on duplication. That separation buys precision at several scales at once: the orchestrator holds the project architecture, dependencies, and tracker state across workstreams; the worker executes at task-level depth across sequential changes or its own delegated subagents, with more capable workers shipping multiple tasks back-to-back; the manager keeps prose, ticket updates, and team communications coherent across streams; and the adviser is a focus point for blockers at any scale, from a single ambiguous diff line to a workstream whose merge requests contradict each other to a project design that quietly assumes code that is no longer on any branch. The orchestrator hands a blocker off with a pointer and keeps coordinating; the adviser returns a verdict plus evidence without loading the sources into the coordinating session. Control and alignment between tasks stay with the orchestrator, and every task result feeds back into the orchestrator's project state so parallel streams stay consistent.

1.3 The tracker tree as shared substrate
The tracker tree makes the scale separation work. Each artifact gives a different slice of state at a different scale: the README and Related Context table serve the project scale; progress.md workstream tables and mrs.md serve the stream scale; variables.md and findings files serve the task scale. Agents read the slice their role needs, no more. The Manager role exists, in part, to give the roster self-correction: a perspective structurally separate from the orchestrator's loop that can spot drift in what the loop itself is producing, before the human or an error in code surfaces it. Without that check the roster is only as self-consistent as the orchestrator's own best day.

1.4 Cost and context efficiency
Cost and context are where the setup wins, not where it pays a premium. A single frontier model on a hard problem tends to spiral: the context grows past 700K tokens, every turn re-reads all of it, the model starts thrashing between half-remembered attempts, and one stuck session can cost more than a full day of the roster and still not land the fix. The roster inverts that. Each session stays partitioned and lean, rarely past 300K tokens, so no session ever pays the per-turn tax of a bloated window. Most of the volume runs on cheap or flat-rate models (the manager on a flat-rate provider, the orchestrator, Flash or Sonnet subagents for reconnaissance and mechanical work), the implementation model stays focused on bounded changes, and the most expensive model is spent surgically as an oracle: a review, a disambiguation, a root cause, then back out. The pairing scales down as well as up: a cheap, fast workhorse plus a small dose of the oracle completes almost any single task at a fraction of what one frontier model alone would spend on it. Imagine instead asking the most expensive model to do the coordination itself: every routine tracker update, every trivial status check, every re-route decision runs on top-tier frontier pricing across the same bloated window, and the bill outpaces the value immediately. The whole point of the roster is that top-tier capacity is rationed to the moments that genuinely need it.

1.5 Structural self-correction
A single model has no structural self-correction. Once a single model's context drifts, commits to a wrong assumption, or anchors on a misread error message, every later turn is produced from the same contaminated context, so the model reinforces its own mistake and spends tokens defending it rather than noticing it. Outside feedback (a human, a reviewer, a second terminal with a different model) is the only way out. A roster builds that feedback in: the manager reads the same trackers from a different cognitive angle and calls out drift before an error lands in code, the adviser checks verdicts against evidence rather than against the orchestrator's summary, and the worker hands the orchestrator results it cannot have hallucinated because the diff is already in git. That separation is not a nicety; it is the only place the correction can come from.

1.6 Matching role to model strength
Models have different cognitive strong sides, and the roster matches role to strength. High-horizon synthesis and parallel routing are different skills from careful bounded implementation, and different again from adversarial source disambiguation. The roster picks the role to fit the model rather than the other way around: Gemini 4 Argon excels at high-level orchestration, long-horizon synthesis, and parallel routing, holding project state without being pulled into detail; Claude Opus 5.5 is the strongest hands-on worker for code, charts, and infrastructure, shipping bounded changes back to back; Kimi K3 pairs architectural framing, business alignment, and prose on flat-rate economics so the manager's volume never hits a token ceiling; and Claude Fable 5.1 is unmatched as a surgical adversarial oracle and deep debugger, the model you reach for when a conflict or a complex root-cause question needs disambiguation rather than momentum. Swapping any two of these costs more than tokens; it costs the strength the role was built around.

1.7 What the setup still does not buy
The role boundaries are load-bearing: an orchestrator that routinely deep dives, or a worker that starts coordinating, collapses the roster back into one big expensive context. The trackers are the shared memory; anything not written down is invisible to every other session. And every verdict the roster produces is still a claim about code and telemetry that an experienced engineer should be able to check in minutes, because the roster shortens the search, not the judgment.

1.8 Evidence in practice
Three parallel infrastructure streams in a single control-plane build (codec, multi-environment Terraform, and identity), a multi-cluster platform rollout across clusters, namespaces, IaC, and consoles, and an in-flight product delivery stream spanning four parallel epics. Each ran with parallel workstreams coordinated by one operator and one shared tracker tree. Section 2 gives the concrete roster; the pairing of model to role above is why those rows look the way they do.

2. High-level setup: a Pi roster in Herdr
A long-running initiative runs under the coordination of a small roster of Pi sessions, each pinned to a different model and a different role, each in its own pane of a single Herdr tab. The roster is expandable (add an Adviser for design sign-off, a Manager for prose-heavy streams, additional subagents for parallel reconnaissance) and collapsible (drop the Manager on a tight implementation-only stream). The naming convention is <prefix>-<NNN>[-<role>], where <prefix> is a short project slug (for example payments, auth) and <NNN> is a zero-padded session counter (for example payments-001). Every roster member shares the same <prefix>-<NNN> so intercom messages and Herdr panes are self-identifying.

The optional roles are where the roster earns its keep on larger projects. The Manager is optional because the orchestrator can absorb the business-alignment and prose responsibilities on a small stream: one operator looking at one thread of work usually does not need a second pair of eyes on What We Said Last Sprint. On a bigger project the Manager becomes the thing that keeps the whole session honest: it reads decisions.md and variables.md the way the orchestrator does not have bandwidth to, it spots when a proposed change quietly contradicts a decision the roster ratified last week, and because it sits outside the orchestrator's project-view loop it can call out when the loop itself is producing incoherent output. That second-perspective check is what we mean by self-correction in this guide: the roster's ability to catch its own drift before the human has to, because at least one role is structurally not the one that produced the drift. Without the Manager, that check has to come from the human or from the Adviser after a mistake is already visible in code.

Two rules make the boundaries work in practice:

Merge request descriptions are written by the Main Worker who authored the change (the implementer has the context), and reviewed or polished by the Manager if the message needs prose care. The orchestrator does not write them.

The orchestrator stays out of routine implementation to preserve context. When the orchestrator hits a genuine conflict, ambiguity, or deep debugging question, it escalates to the Adviser rather than long-running its own investigation; that is what keeps the high-level view clean.

2.3 Self-organising inter-agent callbacks
The roster is not centrally scheduled. The orchestrator routes work in, but after that the agents self-organise over pi-intercom: a session that was called by another session calls back on its own initiative when it has something to report, without waiting for the original caller to chase it. The convention applies equally to review passes, design questions, deeper investigations, and hand-offs: when an interactive agent receives a message and finishes the requested work, it pings the sender back with the outcome at the same <prefix>-<NNN> address it received from, even if no explicit "reply when done" instruction was attached.

This is what lets multi-step work compose across the roster without a scheduler watching every step: an Adviser that was asked for an adversarial review returns it over intercom, the Manager who drafted a document sends the path back for publication, the Main Worker signals a pushed MR to whichever session is next in the chain. The contracts that keep this from decaying into noise are the session names themselves (self-addressing, see 2.1), the tracker as the single source of truth for what was done (rather than the intercom transcript), and the role boundaries in 2.2 (so the orchestrator does not double as a chat relay for every message).

2.4 Subagents and codemode
The interactive agents are supplemented by two delegation mechanisms that keep heavy lifting out of the interactive sessions:

pi-subagents spawns bounded, non-interactive child agents. Default models are Sonnet 5.5 and Gemini 3.8 Flash for reconnaissance, codebase searches, test runs, document generation, and mechanical edits. Subagents are worktree-scoped by default; parallel runs across the same tree are forbidden (the "one writer" rule).

codemode runs JavaScript that batches multiple tool calls (Promise.allSettled) inside a single session. Use it for offline delta reconnaissance, multi-file greps, large-output filtering before it hits the session context, and API queries that are cheap to fan out and aggregate.

The roster uses "eager dispatch" by default: route any non-trivial work to a subagent or codemode call, keep the interactive session's context reserved for decisions and user-facing synthesis.

2.5 Typed-decision classifiers (Jev and Laya)
Alongside generative subagents, the setup wires a fast typed-decision classifier tier (hosted Jev or the local Laya model via the pi-local-laya extension). It is hooked directly inside codemode (via tools.classify and models.classify) and can also be invoked from natural language, as well as acting as an automatic risk gate on shell commands that mutate shared or remote state. Instead of free-form generation, it answers typed questions over JSON state in roughly 50 ms at zero LLM token cost: boolean gates, multi-choice triage (for example classifying batches of CI failures, log lines, or review threads), and ordered scoring.

In practice, when strong models are already guiding the session and writing deterministic JS filters in codemode, the incremental value and day-to-day impact of this classifier tier are still an open question to be proven under real workloads.

3. How projects and subprojects are scaffolded
Everything a session needs to remember lives in a plain-markdown tracker folder, one folder per project. The tracker root can live anywhere the operator prefers:

~/.pi/context/ if Pi is the only agent harness in play

~/.pi/agent/context/ if you want trackers grouped with the rest of the Pi agent state

~/work/context/ (or ~/cg/context/, or any other workspace path) if you want trackers co-located with your code checkout

If you run more than one agent harness (for example Pi and another tool that expects its own state directory), symlink each harness's expected path to a single shared directory so every agent reads and writes the same files. The convention matters more than the absolute path: the rest of this guide assumes the tracker tree exists somewhere and that every roster member sees the same tree.

3.1 Hierarchical structure
A project is a folder. A subproject is a subfolder. A deeper feature or phase is a sub-subfolder. The naming pattern <root project> -> <sub-project> -> <sub-sub-project> mirrors the shape of the work: the root project tracks the program or initiative, the subproject tracks one bounded thread of work within it, and the leaves hold the per-feature or per-state documents.

Every project and subproject carries the full backbone set (README.md, index.md, tickets.md, mrs.md, decisions.md, variables.md, progress.md, continuation-prompt.md). Deeper leaves may be leaner (a <sub-sub-project> often only needs README.md, index.md, progress.md, variables.md, and its design or spec document); the naming convention is what matters, not the file count. Two sibling root projects show that the tracker tree is a forest, not a single trunk: each root project is independent and links to siblings only through its README's Related Context table.

3.2 index.md at every folder level
Each folder carries an index.md: a one-paragraph navigation map of every file and subfolder at that level. The index tells a session (or a human) what lives where without needing to ls. The standard we follow:

Folder-level README.md: goal, strategy, scope, and a Related Context table that links parent and sibling trackers without copying their content. One can read README.md at any level and know exactly what that folder tracks and where the neighbours are.

Folder-level index.md: a flat list of everything directly in the folder: every file and every subfolder with a one-line description per entry. It exists at every level so an agent (or a grep) can walk the tree top-down with confidence.

The two files are complementary, not redundant: README.md is about the tracker's purpose and neighbours, index.md is about its contents.

3.3 Standard artifact files at each tracker leaf
Every project or subproject leaf carries the same set of artifact files. The set is fixed by the tracked-project-status skill's templates; consistency across trackers is what makes them predictable for agents and humans.

3.4 How MEMORY.md and SCRATCHPAD.md relate to trackers
Two separate stores of memory exist and serve different scopes:

The tracker folder is the single source of truth for project state. Anything an agent or engineer needs to know about the project lives here: design decisions, open trades, ticket and merge request state, the handoff prompt.

~/.pi/agent/memory/MEMORY.md is the cross-project long-term store. It holds pointers to trackers (tagged #project-<slug> with the tracker path and governing ticket or epic) and durable cross-project rules (role boundaries, doc-publishing rules, issue-tracker hygiene conventions). It does not duplicate tracker content.

~/.pi/agent/memory/SCRATCHPAD.md is the session-internal working list: a checklist of things to fix later or keep in mind for the current session. Scratch entries that survive the session move into memory or into the tracker.

~/.pi/agent/memory/daily/<YYYY-MM-DD>.md is the running day log across all projects; milestone events get an entry here with a #project-<slug> tag so the day view and the project view both hold the same fact.

The contract is: trackers own project state; memory owns rules and pointers; the day log owns chronology. Agents should not store project facts in memory long-form; that is how drift starts.

4. How projects are tracked, progressed, and updated
4.1 Session spin-up: preflight offline state check
Spinning up a new session (<prefix>-<NNN>) starts with an offline delta check before any work begins. The orchestrator (or a spin-up skill, which automates this) collects:

Merge request delta: every MR referenced in the tracker's continuation-prompt.md and mrs.md queried via glab api for merged, closed, or new comment activity since the last session ended. New comments from humans are quoted into the delta report.

Untracked MRs: recently updated MRs in the relevant repos mentioning a tracker ticket key but not yet in mrs.md; these are the drift candidates.

Issue tracker delta: a JQL (or equivalent) over the ticket keys in tickets.md for status, assignee, and priority changes.

Tracker drift: tracker files modified in the window (usually by an earlier roster or by the human between sessions).

Live previous roster: any pane still running from the prior session number.

The orchestrator presents this delta to the human and asks for offline updates (merged MRs they did themselves, Slack or team comms, priority shifts, manual actions). Only after the human confirms or supplements the delta does the orchestrator route work. This preflight exists because the tracker is a mirror of the world, not the world itself; a session started on a stale mirror makes confident wrong calls from minute one.

4.2 Same-turn milestone bookkeeping
Bookkeeping is not deferred. At every milestone (progress made, MR merged, decision ratified, variable surfacing), the tracker updates happen in the same turn as the work itself. In practice:

progress.md gets a row in the session log plus the workstream table updated.

mrs.md gets the MR row updated (merged, closed, new status).

variables.md gets new open trades the moment they surface mid-work, not at session end.

decisions.md gets the new D-n entry alongside the short-name index at the top.

continuation-prompt.md is rewritten at milestone boundaries, not at session end; the next session should be able to start from any milestone.

The rule exists because multi-agent sessions end abruptly. A tracker that is a turn behind is a trap for the next roster member.

4.3 Team-wide tracking on shared initiatives
Initiatives like a major refactor or a cross-repo feature span multiple engineers (Engineer A, Engineer B, Engineer C). The tracker tracks teammates' MRs, branches, and tickets alongside the roster's own. The reason is not surveillance; it is conflict detection:

Two MRs touching the same surface conflict before they merge if both are in mrs.md.

A teammate's branch that renames a shared config format is a dependency for the roster's work; tracking it turns "blocked" into "scheduled".

In-flight design documents authored by other engineers are listed in the tracker's related-context table so nothing gets re-litigated.

4.4 Automation vs human gates
The roster can act autonomously within a defined set of tasks, and must stop and ask at a defined set of gates. The split is documented here so it can be reused across projects.

Agent-driven, no gate needed (within the same turn; the operator is informed after via the tracker):

Issue tracker ticket creation, assignment, and status transitions on the operator's own tickets.

Routine progress comments on the operator's own tickets.

Git worktree and branch operations: commit, push, MR creation.

MR description updates (posted from a file with glab mr update N, never inline via the API, so newlines and backticks survive).

Automated review bots: replying to bot threads, applying bot suggestions, retriggering bot runs.

Telemetry platform, deployment platform, and Kubernetes verification queries.

Local design doc edits and the Confluence republish of pages the agent owns.

Explicit human gates (require the human's GO before the action):

Merging any MR. Bot-review approval resets on every push, so approval right before merge still needs a human GO.

Posting, replying to, or resolving anything a human will read: human MR review threads, ticket comments addressed to other engineers, Slack messages, external announcements. The agent drafts the message, shows the draft, and waits.

Production promotions (deploying images to prod, promoting model pins, flipping traffic).

Posting anything under the human's name that is not a routine status note on their own ticket.

When in doubt, ask. A gate missed is harder to recover from than a turn spent confirming.

5. Skills overview
Three skills carry the weight of the scaffold. Each lives under the Pi agent skills directory and is what makes the roster spin-up and tracking repeatable.

5.1 New Project Creation
Scaffolds a new tracker for a project or subproject from a set of markdown templates. The skill places the new folder under the nearest existing parent in the tracker tree, creates the standard artifact set (including an index.md at every folder level), fills the placeholders with real content, wires the new tracker's Related Context table to its parent and siblings, copies binding decisions into the new decisions.md as inherited (I-n) entries, and seeds the tracker with live state: open MRs from the Git host, tickets from the issue tracker, a first progress.md session-log entry. New projects are registered in a small per-project config so the status-reporting skill below can find them, and a pointer entry goes into MEMORY.md so any session knows where the tracker lives.

5.2 Project Status Tracking
Answers questions like "status report", "where are we", "current state of the project" for any registered project. Reads the tracker's artifacts in a known order, verifies them against cheap live checks (recent MR activity, the deployment platform, the issue tracker's current state), and renders a terse one-table-per-workstream report with state markers and a critical-path summary at the bottom. When live reality has drifted from the tracker the report leads with a one-line delta, shows the live state, and offers to update the artifacts. The format is standardised across projects so a report from one tracker looks like a report from any other.

5.3 New Session Spin-Up
Automates the start of a new roster iteration: discovers the next session number, runs the preflight offline delta (the same checks as section 3.1), creates the Herdr tab with the pane layout, launches the Pi agents with model validation, and sends the orchestrator a kickoff prompt that points at the continuation prompt and the delta report. The skill enforces the human gate at the end: work starts only after the human confirms or supplements the offline delta. Useful flags include a dry-run mode that shows the full plan before doing anything and a preflight-only mode that runs the delta without spinning up.
